# 基线偏离检查与厂商修正配置生成

状态：用户以“继续”确认设计，进入实施；实际完成状态见实施计划及验证证据。

## 目标和已确认需求

用户要求根据现有设备配置备份、基线参数及模块实现，自省完善 baseline：识别配置偏离，并生成对应厂商的修正配置。例如，删除错误的日志服务器、添加正确的日志服务器。举一反三覆盖现有领域，而不是只修一个日志命令。

用户已确认：**修正配置由人工审核后执行**。本库负责离线检查、生成方案及验证依据；不连接设备、不下发、不自动保存或提交设备配置。宿主应用决定执行及持久化方式。

设计者的选择：保持 Ruby gem 和现有 Policy/Audit/Evidence/Report 接口，在现有事实及来源模型上增加配置资源、差异规划及厂商命令呈现。现有审计调用不应因为调用者未请求修正方案而产生额外副作用。

### 补充勘察：需要先固定的审计语义

以下于设计阶段通过当前实现的合成输入复现，尚未修复：

1. `Huawei::Parser` 复用 Comware 日志解析。`info-center loghost source-port 10514` 被当成地址为 `source-port` 的服务器。单个真实日志目标加该命令，`syslog.minimum_servers expected: 2` 从 fail 变成 pass。根因在 Comware 的目标筛选/地址提取将保留命令词当作合法 DNS 名。若同时配置源接口，source-port 还会因 `source\b` 被误当成源接口声明并使该事实 unknown。这与 SSH ACL 日志开关问题属于相同的命令边界/命令分类缺陷。
2. Huawei 官方合法命令 `info-center loghost domain logs.example.invalid` 被解析为 `["domain"]`，而非批准的域名，造成错误偏离。需要厂商自己的目标语法；不能只改一个否定前瞻后继续接受未解析尾部。
3. H3C/Huawei 官方允许 `info-center loghost source loopback 0`。当前源接口只接收一个词元，`LoopBack0` 可通过、分开的接口类型和编号变 unknown。NTP 源接口有同样的单词元约束；应按厂商接口语法解析、规范化与呈现，不能把任意多词字符串直接插入 CLI。

范围限制：本批没有 Huawei 实际备份；逐行扫描未发现上述 source-port、domain 形式或分开的 NTP/Syslog 源接口形式。因此前两项和第三项的分写形式仅有官方语法及合成证据，**不计入真实备份受影响数量**。初步多行扫描因 `\s` 跨行产生的 316 份分写形式计数已经推翻，不应作为后续结论或测试预期。

真实拓扑的另一个约束：79 份 NX-OS 配置有 396 条带 use-vrf 的日志目标声明；17 份 Hillstone 配置有 237 条日志声明，其中 2 份存在同一地址用于不同 vrouter。Hillstone 按地址和 vrouter 粗分只有 38 个组合，说明日志类别/传输等其他维度也必须保留，不能把 237 条折叠成 38 条后再生成删除命令。这是配置形态统计，不是组织批准值。

## 业务不变量

1. 检查与生成共用同一次解析、同一上下文解析结果和策略指纹。方案绑定平台、配置 SHA-256、策略 SHA-256 和上下文，防止错配报告。
2. 配置完整性、事实已知、基线批准值已知、命令语法受支持分别判断。缺失、false、空集合、未知不能相互替代。
3. 每条启用规则都有明确的规划结果：无偏离、已生成、受阻或不适用。不能静默忽略 fail，也不能把有少量命令的方案宣称为全部可修复。
4. 增删对象按完整厂商标识及作用域匹配。相同地址在不同 VRF、日志类别、命名 profile、端口或认证职责下不能错误合并。地址级合规与完整对象级合规明确区分。
5. 保留已经正确的配置和未纳入基线管理范围的配置；不为修复局部字段删除整个 profile、ACL、AAA 组或接口。
6. 明确配置删除与设备默认值不同。没有确定的默认值证据不能把 undo/no/delete 当成设置为 false。
7. 命令输出只能来自受支持的厂商操作模板及经过类型校验的参数。拒绝换行、控制符、视图逃逸和非法词元；不接受任意 CLI 模板字符串。
8. 规划确定、去重、无互相矛盾操作；输入及策略不变时输出相同。目标已经满足时零变更。按支持的状态变换应用方案后再次规划应为零变更。
9. 未知事实、部分备份、冲突批准值、无效策略、未解析共享引用、缺少必需参数时，相关操作受阻；独立领域仍可给出可审核方案。任何受阻项使整体状态为 partial/blocked，不能伪装为 ready。
10. 生成不等于执行、配置生效或业务可用。离线验证与设备实际连通、NTP 同步、日志到达、认证成功分别报告。

## 领域模型与职责

保留 Parser → FactBuilder → Evidence → Evaluator → Report 主链。

- `ConfigurationResource`：不可变的配置对象，包含 kind、完整 identity、scope、规范化 attributes、来源行、已解析程度及引用关系。原始 CLI 和密钥不属于公开资源数据。
- 厂商 Parser 在已有领域解析过程中记录资源，地址集合等旧事实由同一资源数据归纳，避免另外写一套互相漂移的正则。配置历史撤销、重复项和覆盖关系按厂商语义折叠。
- `Remediation`：离线编排入口，持有 policy，与 Audit 共享解析入口；`call(configuration:, platform:, complete: false, context: {})` 返回 `RemediationPlan`。不接受外部 Report 与另一份配置任意拼接。
- `RemediationPlanner`：根据已解析资源、适用策略和规则差异产生领域操作，处理依赖、冲突、顺序及受阻原因；不包含厂商 CLI 分支。
- 厂商 `CommandRenderer`：将受支持的领域操作变为带视图路径的命令步骤。Comware/VRP、IOS/NX-OS 只有语义相同部分共享，保留实际厂商差异。
- `RemediationPlan`：不可变方案，包含 audit、指纹、逐规则结果、结构化操作、阶段、风险、前提、验证项及安全序列化。

这些名称和内部文件拆分由实现者在保持职责不变量的前提下精简，不因文件行数增加层级。

## 基线参数契约

继续支持现有 version: 1、checks、expected 以及 host/model/site/role/vendor 选择逻辑。现有规则与报告含义不静默改变，ctx_parser gemspec 继续不设版本约束。

为需要精确配置的对象增加有类型的结构化规则：

- `syslog.destinations`：目标地址、VRF/vrouter、协议、端口、facility、severity/日志类别、源接口，以及需要时的 profile/server 名称。
- `ntp.associations`：server/peer 类型、地址、VRF、优先级、版本、源接口和认证 key 引用。
- `tacacs.endpoints`：组/方案、认证/授权/计费职责、主备/顺序、地址、端口、VRF、源接口、密钥引用。

结构化对象数组仍经 expected 的上下文选择，缺失字段与显式默认值分别处理。类型、范围、作用域及同一标识重复定义在 Policy 构造时校验。现有地址规则仍可独立使用并生成无歧义的简单修正；存在多作用域或无法确定新增选项时明确受阻，不能任意选一个 VRF 或继承错误目标的参数。

新增可选 `remediation` 策略段只容纳生成所需而非合规要求的参数：管理对象名称/ID、允许修改的作用域、排序选择、厂商语法 profile、秘密引用。版本 1 的原有文档仍有效；新字段必须有严格白名单与类型检查。

### 对象集合、字段省略与使用关系的确定语义

以下为设计者按最小必要变更原则作出的选择，不是用户另行提出的要求：

- 结构化规则的 expected 数组表示**明确受管作用域内对象标识的完整期望集合**，不是仅追加集合。受管作用域通过该规则的 remediation 参数显式声明；允许按现有上下文选择器解析。作用域未声明时可以审计声明的对象是否存在，但不生成删除额外对象的操作，并返回 missing_managed_scope。空 expected 表示清空明确受管作用域，不表示清空全设备。
- 对象省略 VRF 指默认路由域，不是任意 VRF；命名 profile/组/对象是该平台身份的必要部分时必须填写，缺少时拒绝策略或标记缺少生成参数。禁止默认通配全部 profile 或全部端点。对象所在作用域不在批准受管范围内时是策略冲突，不能越界执行。
- 身份字段必须完整；非身份字段省略表示不要求、不比较、不主动修改。更新现有对象时保留这些字段；新增时使用适用语法 profile 有官方依据的默认值，必需且无可靠默认值的字段必须显式补齐，否则受阻。明示值与有效默认值可规范化为相同含义，但不能从其他服务器复制未批准选项。
- 对定义对象和使用关系分别建模。结构化对象可附 `bindings` 数组，指定批准的日志类别、认证域、VTY 或管理端点等领域引用目标；值由厂商白名单及类型校验，不接受任意配置路径字符串。绑定是期望状态的一部分，引用错误或未引用必须 fail；存在未知引用则 unknown/blocked。只有对象定义、未声明 bindings 时，只声明对象定义层面的合规，输出明确注明未验证使用链，不能称日志或认证功能完整。
- 作用域中当前存在的有效使用关系不能因为未写 bindings 而被删除。修改/移除被引用对象时，必须先保留、迁移或明确批准移除这些关系；没有批准的新引用目标时受阻。旧地址规则仍保持地址检查语义，不静默升级为使用链合规。

### 来源范围采用上限语义

现有 management.sources/snmp.sources 的 networks_within 语义保持：批准网段是最大允许范围，较窄的当前许可不能被自动扩大。若只需剔除越界来源，新 ACL 的允许集合取**当前有效许可范围与批准范围的交集**，在完整证据下计算，保留协议、端口和端点差异；禁止直接放开全部批准网段。

如果现有来源不能确定，或缺 ACL 而需要首次建立允许来源，生成器要求显式 `remediation` 中的 `access_targets`（按受管端点列出的实际目标允许范围），并验证其在已解析批准上限以内。没有上限或没有首次建立所需的目标时受阻，不凭空决定开放哪些主机。access_targets 是操作意图；新 ACL 及其绑定完成后仍按既有范围规则重查，不改变旧审计比较语义。明确要求精确允许集合的审计能力应新增独立规则，不重定义 networks_within。

地址规则与结构化规则一起启用时校验一致性；例如批准地址 A 与批准目的对象 B 不能生成同时新增/删除的方案。数量规则只规定数量，不能据此编造服务器地址；若没有批准清单，返回 missing_approved_targets。

非秘密的命令参数与秘密引用分开。密文不能证明口令强度；不从备份恢复或重用密钥。需要新秘密的变更显示 required_secret 等前提；普通 to_h/to_text/inspect 不包含秘密。若以后需要带秘密的执行产物，应另设显式凭据提供及受控导出入口；本次不生成含待替换占位符、却标记可执行的命令。

## 全领域处理要求

覆盖现有全部 30 条规则及新增结构化对象规则，不把首个 Syslog 场景当成全部完成。

| 领域 | 需要完成的检查与配置生成 | 缺前提时的行为 |
| --- | --- | --- |
| Syslog | 对批准目标集合增删、同对象选项修改、源接口纠正、保留命名 profile 和类别关系；识别 profile 定义但未被输出路径使用 | 缺 profile/作用域/传输参数或未知语法时受阻，不能删除整个 profile |
| NTP | 区分 server/peer，批准对象同步、源接口、认证配置及 key 引用依赖 | 无批准地址或认证材料时列出所缺参数，不仅打开认证开关 |
| SSH/服务 | 支持的开关、版本、VTY 协议、认证方式和目标端点修改；区分管理接口及数据接口 | 缺密钥、AAA 链、端点或默认值证据时受阻；不臆造 RSA 密钥或开启全部接口 |
| 管理/SNMP ACL | 有序 IPv4 来源范围、绑定对象、协议/端口、共享引用；为目标端点构造保留更严许可且不越过批准上限的专用 ACL，再绑定 | 未批准 ACL ID/名称、首次建立所需 access_targets、共享引用不明、复杂匹配语法、IPv6 不支持范围时受阻；不直接覆盖现有共享 ACL |
| SNMP | 服务及版本、禁止写、v3 authPriv、来源限制、用户/组/视图引用 | 需要新用户/秘密时明确缺参；不得仅删除全部 SNMP 配置以“通过”子规则，必须检查与 enabled 等规则一致性 |
| TACACS | 目标、主备/职责/组、密钥引用、登录/授权/计费引用链及本地后备 | 不可只创建服务器而漏掉实际引用；变更认证链列高风险，缺目标/组/秘密或未解析引用则受阻 |
| 凭据 | 明文/旧算法储存与可观察强度偏离、需要轮换的对象及依赖 | 不从 hash 推断强度、不生成默认密码；缺批准的新凭据时受阻，仍给出明确修复需求 |

每个厂商建立规则级“可审计 / 可生成 / 条件生成 / 未支持”矩阵，附稳定 reason；Audit.capabilities 的既有含义保持，增加 Remediation.capabilities 查询生成前提。

范围包含当前六类适配器及别名；Huawei 使用合成样本及官方语法，不声称真实备份覆盖。对备份出现的 Centec、Radware，先辨认产品/版本和语法，研究并扩展可被官方依据与样本证明的领域；不能把相似命令直接映射到 Cisco。无法证明的能力显式保留 unsupported，列入交付缺口，不以“无报错”算支持。

## 方案内容及命令顺序

每条规则返回 status（not_needed/planned/blocked/not_applicable）、reason、missing/unexpected/changed 差异、相关操作 ID、所缺参数和来源行。

整体状态：noop（所有适用规则已满足且无受阻项）、ready（存在命令且所有需要处理的偏离均已覆盖）、partial（有命令也有受阻项）、blocked（无可生成命令且有受阻项）。另标记 requires_review，所有非空方案均需人工审核。已有 unknown 也必须在覆盖状态中显示，不能用 ready 暗示完整合规。

阶段：前提检查 → 建立新增对象 → 切换引用/修改字段 → 移除不再批准的对象 → 验证。默认先增后删以减少中断；按基线安全需求可选先撤销未批准目标，差异和顺序必须显式可见。容量限制、同标识只能替换、依赖和共享引用优先于一般排序，无法得出有效顺序则受阻。

呈现包含进入视图、命令、退出视图，不混入设备提示符或交互确认。PAN-OS 等候选配置平台的 commit、Cisco copy/save、Comware save 等放在单独人工操作提示，默认修正命令块不自动提交/保存。厂商验证命令独立展示，不能混入修正块。

回退仅对可逆且旧值完整的非秘密修改提供逆操作。涉及轮换、缺失旧状态或不可逆步骤，明确不可完整回退，不输出伪造 rollback。

## Syslog 验收示例

合成设备现有 192.0.2.20 和 192.0.2.30，基线批准 192.0.2.20 和 192.0.2.40：保留 .20，增加 .40，删除 .30。H3C 的简单全局示例是 `info-center loghost 192.0.2.40` 与 `undo info-center loghost 192.0.2.30`，按方案顺序呈现。

带 VRF、协议、端口、facility、日志类别的对象按完整身份同步；新对象选项来自明确批准参数。Hillstone 删除不能只给地址；PAN-OS 修改应定位到 profile/server 叶子，不删除无关 profile 配置。只修改端口时报告 changed 而非把地址当作已合规。

重复目标、不完整输入、无批准值、scope 未命中、已合规、空批准集合（明确要求删除全部该受管范围）、不合法目标、同地址不同 VRF、共享引用、删除不存在对象和冲突策略均有独立验收。

## 验证及交付

1. 已知 ACL 缺陷、Huawei 日志 source-port/domain 误分类及单词元接口约束补回归；同类命令分类应区分服务器目标、源接口、源端口及其他日志控制项，保留正确语法及局部未知诊断。确认 source-port 不能增加服务器数量。
2. 配置资源提取：六平台合成 fixtures；完整 identity、选项、继承/撤销、来源、未知标记和秘密不泄漏。
